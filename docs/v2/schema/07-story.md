## What survives from current FCP

The recap publication model is the **best-realized piece of the existing codebase** and it survives essentially intact:

- **Facts and prose are separate objects**, separately versioned.
- Editions reference an immutable fact snapshot by id.
- A partial unique index guarantees exactly one published edition per period.
- Publish is atomic and checks admin rights inside the transaction.

Charter Decision 13 states the rule this design already implements: *an LLM may turn facts into compelling editorial output; an LLM should never be the authoritative source of standings, awards, transactions, rankings, matchup results, or other factual league state.*

Keep the shape. What changes is the substrate it sits on — the facts now come from canonical tables with finality and lineage rather than from a three-way reconciliation across overlapping snapshot tables with layered try/except fallbacks.

## Tables

### `story_facts`

**Scope:** `league_season` · **Freshness:** `final` once frozen

```sql
create table story_facts (
  id                    uuid primary key,
  league_season_id      uuid not null references league_seasons(id),
  matchup_period_id     uuid not null references matchup_periods(id),
  version               int not null,
  metric_definition_id  uuid not null references metric_definitions(id),

  facts                 jsonb not null,       -- the deterministic fact bundle
  warnings              jsonb not null default '[]',
  status                computation_status not null,
  reason                text null,

  frozen_at             timestamptz not null default now(),
  created_by_user_id    uuid null references users(id),
  unique (league_season_id, matchup_period_id, version)
);
```

Notes:

- **Immutable.** A regeneration produces a new `version`, never an edit.
- `metric_definition_id` versions the *assembly*, not just the numbers. When fact assembly changes — a new award, a corrected all-play rule — old editions stay attributable to the assembler that produced them.
- `warnings` and `status` carry data-quality honestly. Current FCP already does this well (`data_warnings_json`, readiness checks) and it should not regress.
- The bundle is `jsonb` deliberately: it is a denormalised, frozen view assembled *from* the canonical tables, read whole, never queried by field. The canonical tables remain the source of truth; this is a citation of them at a moment in time.

### `story_editions`

**Scope:** `league_season` · **Freshness:** `final`

```sql
create type edition_status as enum ('draft', 'published', 'superseded');

create table story_editions (
  id                    uuid primary key,
  league_season_id      uuid not null references league_seasons(id),
  matchup_period_id     uuid not null references matchup_periods(id),
  story_facts_id        uuid not null references story_facts(id),
  version               int not null,
  status                edition_status not null default 'draft',

  content               jsonb not null,        -- structured editorial output
  generator             text not null,         -- model id / prompt version
  generation_meta       jsonb not null default '{}',   -- tokens, latency, retries

  created_by_user_id    uuid null references users(id),
  created_at            timestamptz not null default now(),
  published_at          timestamptz null,
  published_by_user_id  uuid null references users(id),
  unique (league_season_id, matchup_period_id, version)
);

create unique index story_editions_one_published_idx
  on story_editions (league_season_id, matchup_period_id)
  where status = 'published';
```

The partial unique index is the invariant that matters and it is enforced by the database, not by application care. Ported directly from current FCP, where it is correct.

`generator` and `generation_meta` are new: which model and prompt version wrote this, what it cost. Charter Decision 28 applied to LLM output — a recap generated by a fallback model after three retries is a different artifact from a clean first-pass generation, and the product should be able to tell.

**Publishing stays a database function.** Current FCP's `publish_recap_edition` does `SELECT … FOR UPDATE`, checks admin rights, supersedes the prior published edition and publishes the new one, all in one transaction. That is the right shape and should be ported.

### `power_rankings` and `power_ranking_entries`

**Scope:** `league_season` · **Freshness:** `derived`

```sql
create table power_rankings (
  id                    uuid primary key,
  league_season_id      uuid not null references league_seasons(id),
  matchup_period_id     uuid not null references matchup_periods(id),
  metric_definition_id  uuid not null references metric_definitions(id),
  projection_freeze_id  uuid null references projection_freezes(id),
  status                computation_status not null,
  reason                text null,
  computed_at           timestamptz not null default now(),
  unique (league_season_id, matchup_period_id, metric_definition_id)
);

create table power_ranking_entries (
  id                      uuid primary key,
  power_ranking_id        uuid not null references power_rankings(id),
  fantasy_team_season_id  uuid not null references fantasy_team_seasons(id),
  rank                    int not null,
  score                   numeric(10,4) not null,
  previous_rank           int null,
  movement                int null,
  components              jsonb not null default '{}',   -- why this score
  blurb                   text null,
  blurb_generator         text null,
  unique (power_ranking_id, fantasy_team_season_id)
);
```

Notes:

- Versioned by `metric_definition_id`, so a ranking methodology change does not silently rewrite history. Charter Decision 21's clearest use case.
- `components` makes a ranking explicable — which is the difference between a number and a story.
- `blurb` is LLM output attached to a deterministic entry, never the source of the rank. Current FCP caches these per week for cost reasons and that instinct is right; here the cache is just the row.

### `league_records`

**Scope:** `league` (spans seasons) · **Freshness:** `derived`

```sql
create table league_records (
  id                      uuid primary key,
  league_id               uuid not null references leagues(id),
  metric_definition_id    uuid not null references metric_definitions(id),
  record_key              text not null,     -- highest_week_score, longest_win_streak
  scope                   text not null,     -- all_time | season
  league_season_id        uuid null references league_seasons(id),

  value                   numeric(14,4) not null,
  holder_team_season_id   uuid null references fantasy_team_seasons(id),
  holder_manager_id       uuid null references managers(id),
  holder_player_id        uuid null references players(id),
  achieved_at             timestamptz null,
  matchup_period_id       uuid null references matchup_periods(id),

  superseded_by_id        uuid null references league_records(id),
  superseded_at           timestamptz null,
  computed_at             timestamptz not null default now()
);

create index league_records_active_idx
  on league_records (league_id, record_key) where superseded_at is null;
```

Attached to `leagues`, not `league_seasons` — records are the payoff of charter Decision 8. A broken record supersedes rather than overwrites, so "who held it before" is part of the story rather than a casualty of it.

### `rivalries`

**Scope:** `league` · **Freshness:** `derived`

```sql
create table rivalries (
  id                    uuid primary key,
  league_id             uuid not null references leagues(id),
  team_a_id             uuid not null references fantasy_teams(id),
  team_b_id             uuid not null references fantasy_teams(id),
  metric_definition_id  uuid not null references metric_definitions(id),

  meetings              int not null default 0,
  team_a_wins           int not null default 0,
  team_b_wins           int not null default 0,
  ties                  int not null default 0,
  last_meeting_period_id uuid null references matchup_periods(id),
  intensity_score       numeric(8,4) null,
  detail                jsonb not null default '{}',

  status                computation_status not null,
  reason                text null,
  computed_at           timestamptz not null default now(),
  check (team_a_id < team_b_id),
  unique (league_id, team_a_id, team_b_id, metric_definition_id)
);
```

Keyed on `fantasy_teams` (the franchise), so a rivalry survives renames and ownership changes. The `team_a_id < team_b_id` check makes the pair canonical so a rivalry cannot be stored twice in opposite order.

### `timeline_entries`

**Scope:** `league_season` · **Freshness:** `derived`

```sql
create table timeline_entries (
  id                      uuid primary key,
  league_season_id        uuid not null references league_seasons(id),
  matchup_period_id       uuid null references matchup_periods(id),
  occurred_at             timestamptz not null,
  kind                    text not null,     -- upset|streak|record|trade|milestone|collapse
  significance            int not null default 0,

  league_event_id         uuid null references league_events(id),
  subject_team_season_id  uuid null references fantasy_team_seasons(id),
  subject_manager_id      uuid null references managers(id),
  subject_player_id       uuid null references players(id),

  headline                text not null,
  body                    text null,
  generator               text null,
  detail                  jsonb not null default '{}',

  metric_definition_id    uuid not null references metric_definitions(id),
  computed_at             timestamptz not null default now()
);

create index timeline_entries_season_time_idx
  on timeline_entries (league_season_id, occurred_at desc);

create index timeline_entries_significance_idx
  on timeline_entries (league_season_id, significance desc, occurred_at desc);
```

The reader-facing spine of "follow the league together." Notice the direction: `league_events` ([`02`](02-fantasy.md)) records *that something happened* as raw fact; a timeline entry is the *derived, ranked, narrated* view of it, with `significance` deciding what surfaces. Events are input; timeline entries are output. Regenerating the timeline under a better significance model never touches the events.

Multi-season history (charter Decision 13's closing requirement) is a query across `league_seasons` for one `league_id`, ordered by time.

## Naming note

Current FCP calls these `recap_facts` / `recap_editions`, and the UI calls the surface the *Newsroom*. The charter uses *story engine*, *timeline* and *newsroom* in different places.

Proposed here: `story_facts` / `story_editions` for the tables, because the domain is broader than weekly recaps — the timeline, records and rivalries are the same engine. **Pick one vocabulary before implementation and use it in tables, API paths and UI copy alike**; charter §21 asks that a new agent be able to answer "where does X live" without archaeology, and three names for one concept is exactly how that fails.

## Open questions

1. **Vocabulary (blocking, above).** Newsroom, recap, story, timeline — settle it now, it touches every layer.
2. **Timeline generation cadence.** Recompute on period finalization, or continuously during a live period? Recommend on finalization for V1: it is cheap, deterministic, and avoids narrating a game that has not finished. Live in-period narration is a later feature.
3. **Records backfill.** Records are derived, so they can be computed for any imported history — but only for seasons actually ingested. With V2 starting empty (charter Decision 25), records begin at whatever history is imported. Worth deciding how many prior seasons to import for the first real league, since it determines whether the records surface is interesting on day one.
4. **Significance model.** `significance` drives what surfaces in the timeline, and a bad model makes the product boring rather than wrong. It should be a versioned `metric_definition` from the start so it can be tuned against real reader response without rewriting history.
